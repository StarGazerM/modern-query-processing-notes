# `code_string!`: the smallest course-style procedural-macro project

Run the example from this directory:

```console
cargo run -p stringify-demo
```

It prints:

```text
1 + 1
x
relation road(City, City);
2
```

The first three lines are textual renderings of code that the macro received as
tokens. The last line is the value computed when the program runs. The relation
declaration is not an ordinary Rust expression; a macro may still receive it
because Rust passes the tokens inside `!(...)` to the procedural macro before
trying to treat those tokens as an expression.

## Why there are two crates

```text
rust-01-stringify/
├── Cargo.toml
├── Cargo.lock                 generated by Cargo
├── stringify-macro/          the compile-time package
│   ├── Cargo.toml
│   └── src/lib.rs            a procedural-macro library crate
└── demo/                     the runtime package
    ├── Cargo.toml
    └── src/main.rs           an executable binary crate
```

A procedural macro must already be compiled before Rust can use it while
compiling another crate, so the macro and its caller cannot be the same crate.
This example places those two crates in separate packages and uses the top
`Cargo.toml` only to build them together. `stringify-macro` contains the
compile-time macro; `demo` contains the executable that invokes it.

The macro package's `proc-macro = true` setting gives rustc a procedural-macro
library to load. The demo's path dependency makes that local macro crate
available and establishes that it must be built first.

Rust itself already has a built-in `stringify!`. This example uses the distinct
name `code_string!` so that deleting the import produces a real error instead of
silently switching to the built-in macro.

## Course procedural-macro style

The exported `#[proc_macro]` function is a thin compiler boundary:

- accept and return `proc_macro::TokenStream`, as `rustc` requires;
- convert the input once to `proc_macro2::TokenStream` for the implementation;
- use Syn 2 types for typed syntax, and use `syn::parse2` when incoming tokens
  must become a typed value;
- emit Rust with a visible `quote! { ... }` template; and
- convert the emitted token stream once back to `proc_macro::TokenStream`.

In this first macro, only the output is typed. The incoming code becomes a
`String`; `syn::LitStr` then represents the output string literal; and `quote!`
emits it. The next workspace replaces that lossy input step first with
`syn::parse2::<IntegerExpr>(input)`, then with the derived `EvalAndCompare`
source shape. The same pattern later reaches
`syn::parse2::<RelationDecl>(input)`. We do not
hand-assemble `TokenTree` output unless token mechanics are themselves the topic
being taught.

## Inspect the expansion in VS Code

Open the notes repository root as the folder in VS Code. In the teaching
checkout this is `doc/notes`; in a standalone clone it is the clone's top
directory. The checked-in `.vscode/settings.json` links rust-analyzer to this
example's workspace manifest, so both the macro and demo crates are analyzed
without opening the example as a separate window. If prompted, install the
recommended **rust-analyzer** extension.

Then open `examples/rust-01-stringify/demo/src/main.rs`, put the caret on a
`code_string!(...)` invocation, open the Command Palette, and run
**rust-analyzer: Expand macro recursively at caret**. The expansion is a
string-literal expression such as `"1 + 1"`. This view is evidence of the
replacement source that the compiler sees; it is not runtime output.
